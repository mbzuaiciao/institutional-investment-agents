# Evaluation framework

## Why prose quality is insufficient

A polished memo can be incomplete, unsupported, numerically wrong, or operationally expensive. It can conceal contradictions behind fluent synthesis and receive a favorable subjective rating despite weak evidence. Conversely, a terse artifact may be highly reproducible and well grounded. Evaluating only the final prose therefore rewards presentation without establishing whether the research process improved.

The workbench evaluates architecture at several layers. The current capstone metrics are calculated in [`workflow.py`](../src/institutional_investment_agents/workflow.py) and aggregated by [`evaluation.py`](../src/institutional_investment_agents/evaluation.py). Tests cover additional mechanical properties. Some intended metrics remain future instrumentation; those distinctions are explicit below.

## Research quality

- **Task completion** is the fraction of planned research tasks marked complete. It detects missing workflow coverage but does not judge whether a completed task was done well.
- **Correct calculations** are checked directly in [`tests/test_tools.py`](../tests/test_tools.py), including spreads, ratios, expected loss, DV01, and scenario impact. The capstone does not currently aggregate a per-run calculation-accuracy metric because deterministic tools are treated as tested infrastructure.
- **Thesis direction** compares the conclusion—attractive or unattractive—with synthetic issuer ground truth. It is emitted as `directional_accuracy`.
- **Risk-factor recall** measures the fraction of synthetic known risk labels present in the thesis. It rewards downside coverage but inherits the limits of author-defined labels.
- **Scenario coverage** is represented structurally through bull, base, and bear `Scenario` objects. The current capstone does not emit a separate scenario-coverage score; adding one would require explicit ground-truth scenario requirements.

The composite `research_quality_score` weights thesis direction at 30%, risk recall at 25%, claim support at 25%, and task completion at 20%. It is transparent and useful for comparison, but the weights are normative. Component metrics remain the primary evidence.

## Evidence quality

- **Claim support rate** is the fraction of claims with valid evidence or traced tool results.
- **Citation validity** is the fraction of evidence pointers that exist and pass the verifier’s lexical-support heuristic.
- **Evidence coverage** is the fraction of retrieved state evidence used by at least one claim.
- **Unsupported claims** counts claims without acceptable support.
- **Contradictions** reports unresolved entries in structured state.

[`verification.py`](../src/institutional_investment_agents/verification.py) implements these checks. Citation validity is not semantic entailment: token overlap can miss paraphrases or accept superficially related text. The metric should be treated as a mechanical screening control.

## Agent behavior

- **Routing accuracy** is implemented in [`routing.py`](../src/institutional_investment_agents/routing.py) and tested against the typed plan. It is not currently included in each capstone summary row.
- **Tool-call count** is emitted from audit events and serves as a transparent activity/cost proxy.
- **Duplicate work** is an intended metric but is not yet instrumented. Detecting it requires defining semantic equivalence between tasks or contributions.
- **Unresolved contradictions** is emitted through the verification result and capstone metrics.
- **Revisions** are supported conceptually by challenge and approval states, but the deterministic workflow does not currently execute a revision loop or emit a revision count.

This category matters because two systems can reach the same answer with different failure surfaces and operational burdens.

## Operational properties

- **Workflow steps** count sequenced audit events. More steps are not automatically better.
- **Reproducibility** is tested by comparing complete states, memos, and metrics for identical seeds.
- **Deterministic behavior** comes from fixed seeds, local data, deterministic retrieval, validated tools, and explicit policies. Checked-in capstone files can be regenerated byte-for-byte.
- **Model-call abstraction** is provided through `ModelBackend`; the default workflow does not claim a paid-model call count.
- **Latency and cost abstraction** currently uses steps and tool calls as proxies. No precise token, dollar, or wall-clock cost is fabricated when no production model API is used.

## Interpreting the benchmark

An architecture should be judged on a vector of properties rather than a single ranking. Verification can improve auditability without changing conclusion quality. A critic can improve risk recall while adding a step. Specialization can alter ownership without changing behavior. These differences are lost when evaluation considers only the final paragraph or one composite score.

The complete experiment design is documented in [experiment design](experiment_design.md), and current numerical results are in [results and findings](results_and_findings.md).

## Phase 2 additions

Phase 2 records injected, detected, resolved, and unresolved failures; calculation accuracy; contradiction detection; stale-evidence use; inappropriate confidence; correct and unnecessary revisions; false challenges; and separate answer/control quality. `ConfidenceComponents` decomposes evidence, calculation, retrieval, consistency, and model judgment into explicitly uncalibrated heuristic scores.

`CostAccount` records model calls, tool calls, retrieval operations, workflow steps, critic/verifier calls, revision cycles, simulated token units, and abstract cost units. Real adapters can record provider-returned usage metadata. Factorial reports include means, standard deviations, approximate confidence intervals, model/harness/interaction decomposition, and per-run records. The [failure taxonomy](failure_taxonomy.md) connects metrics to causal failure surfaces.
